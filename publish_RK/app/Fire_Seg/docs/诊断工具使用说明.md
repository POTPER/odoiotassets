# V20 诊断工具使用说明

工具位于 `tools/check_device.py`，以 V20 目录为基准查找模型、字体和配套源码，不依赖旧 `Fire_Seg_yolo26` 文件夹或旧入口。

下列命令在 RK3588 的 `Fire_Seg_V20` 目录内执行。工具不安装依赖、不改变系统配置，不发送 UDP，不驱动蜂鸣器或云台。默认只读取信息、校验文件和写入诊断 JSON；实际 NPU 与摄像头测试必须显式指定参数。

## 1. 默认检查

```bash
python3 tools/check_device.py
```

检查内容：

- Python、Linux ARM64、可读取的设备树信息。
- NumPy、OpenCV、Pillow、RKNNLite 是否可导入；PyYAML 仅用于 YAML 元数据。
- RKNN 文件、类别顺序、火焰类别、输入尺寸、输出格式、目标平台及元数据绑定哈希。
- 学生入口、共用模块、字体和蜂鸣器驱动文件是否存在；答案入口缺失为提醒，允许学生单独部署。
- Python 源码的语法和字体加载。只解析源码，不执行学生判断函数，也不判断 TODO 答案对错。
- 可找到的 RKNN Runtime 库、NPU 设备/驱动线索、摄像头设备列表与权限。

报告默认保存到 `output/device_check.json`。再次运行会更新该报告；需要保留旧报告时指定另一个名称：

```bash
python3 tools/check_device.py --json output/device_check_before_test.json
```

默认报告中的 `npu_probe` 和 `camera_probe` 为 `SKIP`，即使文件检查通过，也不代表真实推理和摄像头已经通过。

## 2. 查看摄像头清单和实际取帧

仅列出设备，不打开摄像头：

```bash
python3 tools/check_device.py --list-cameras
```

实际打开一个指定摄像头并读取一帧：

```bash
python3 tools/check_device.py --camera 41
# 或指定设备路径
python3 tools/check_device.py --camera /dev/video41
```

请先关闭占用同一摄像头的识别程序。编号 41 是当前实训箱配置，换设备后应按实际清单选择；存在 `/dev/videoN` 不代表该节点一定能输出图像。该探测使用 OpenCV 默认采集配置，只验证一次打开和取帧，不验证入口中的分辨率回退策略或长期帧率。

## 3. 实际 NPU 推理检查

```bash
python3 tools/check_device.py --npu-test --image testimg/fire1.jpg --core all
```

使用包内 RKNN 和图片，验证 RKNNLite 加载、真实输出解析及推理调用；不允许回退 CPU。不要求图片必须检出火焰才算执行通过，识别准确性仍需看实际图像和识别结果。

默认先运行一次，额外预热 3 次，再记录 10 次耗时。可以减少次数：

```bash
python3 tools/check_device.py --npu-test --warmup 1 --runs 3 --core auto
```

报告区分初始化、首次推理、预热后的耗时，以及完整预测流程与 `RKNNLite.inference` 调用耗时。后者也是调用墙钟时间，不能当成纯 NPU 硬件时钟，更不能据此证明全部算子均在 NPU 执行。

NPU 和摄像头探测在独立子进程运行，各自默认超时 30 秒，超过时限终止探测进程并记失败。可用 `--timeout 60` 调整。两项也可一次请求：

```bash
python3 tools/check_device.py --npu-test --camera 41 --core all
```

诊断时不运行学生或答案入口，不会产生教学成果 CSV。工具只保存诊断 JSON；不输出检测标注图。需要看单张图识别效果时，在 V20 目录运行：

```bash
python3 fire_yolo26_v20.py --source testimg/fire1.jpg
```

单张图结果进入 `output_v20`。这不是文件夹批量识别，也不能代替四项摄像头成果验证。

## 4. 检查候选模型

把候选模型及真实元数据放在独立目录中，再指定路径，不覆盖现用模型：

```bash
python3 tools/check_device.py --model candidate/fire_candidate.rknn
python3 tools/check_device.py --model candidate/fire_candidate.rknn --npu-test --core all
```

类别、输入输出格式应使用候选模型真实导出信息。只有确认类别顺序时才能手动指定，例如本次原模型训练顺序为 `0=fire, 1=smoke`：

```bash
python3 tools/check_device.py --labels fire smoke --fire-class 0 --npu-test
```

不要为消除错误而随意填标签或输出格式，也不要删除 `smoke` 标签改变编号。当前 V20 模型的真实输出为 `(1, 6, 8400)`，格式为 `ultralytics_raw`。

## 5. 如何读结果

| 标记 | 意义 |
|---|---|
| `PASS` | 该项在检查范围内通过 |
| `WARN` | 有待核实的信息或非必需项缺失 |
| `FAIL` | 该项不满足部署或探测要求，报告保留异常说明 |
| `SKIP` | 未请求或前置条件不成立，该项未验证 |

存在 `FAIL` 时工具返回退出码 1；没有 `FAIL` 时返回 0。部分项目失败仍会继续汇总其他项目并尝试保存 JSON。Windows 电脑上的 Linux ARM64、RKNNLite、NPU 项失败属于运行平台不符合板端要求，并不说明检查工具本身运行异常。

## 6. 常见问题

| 现象 | 处理方向 |
|---|---|
| 模型不存在、模型哈希不一致 | 核对模型和同名 JSON 是否成套；哈希检查不能证明模型精度 |
| 类别名称为空、无法确定火焰类别 | 使用训练时的真实类别顺序，优先恢复正确元数据 |
| 学生入口语法失败 | 按报告行号检查缩进、括号和冒号；工具不会导入学生入口，其他项目仍能继续 |
| 字体缺失或加载失败 | 恢复 `Arial-Unicode.ttf`，检查 Pillow 环境；文件存在仍不等于画面文字已现场确认 |
| 缺少 RKNNLite 或 Runtime | 沿用板厂匹配的 ARM64 环境，核对 Python、ToolkitLite、Runtime 与驱动版本 |
| 静态模型提示 dynamic range 查询失败 | 当前模型为固定输入尺寸；单独此警告不能证明推理失败，应看初始化及实际 NPU 探测结果 |
| 摄像头无法打开、读不到帧 | 核对实际节点、权限、设备占用及采集格式，再看入口的采集日志 |
| 驱动文件存在但蜂鸣器不响 | 文件检查不触发声音；使用答案入口完成现场联动检查，核对模块编号、电源和接线 |

板端依赖见根目录 `requirements.txt`。正常 V20 推理不需要 Ultralytics、PyTorch 或 ONNX Runtime；这些属于另行准备的模型转换环境。
